# Architecture and operating boundaries

- `cli.js`: local configuration, transactional SQLite single-process lease, Socket Mode connection, explicit envelope acknowledgment, worker/outbox timers, diagnostics.
- `protocol.js`: anchored bot command grammar and options parsed only before `--`; output escaping.
- `store.js`: SQLite WAL, event deduplication, task/job state and durable outbox. State files are private; no secret token values belong in the database.
- `repository-router.js`: authoritative Slack channel metadata lookup, exact case-insensitive repository-name matching over paginated `gh` results, owner/hint filtering, permission checks, optional validated local checkout reuse, and GitHub-ID-keyed managed clones.
- `bridge.js`: authorization, immutable thread/repository binding, owner/operator controls, serial queue, bounded phase orchestration, cancellation and recovery.
- `runner.js`: supported CLI invocation through argument arrays and stdin; explicit models; safe environment forwarding; bounded JSONL and final output; process-group timeout/cancellation.
- `git.js`: worktree preparation and crash reconciliation, guard checkpoints, remote verification, explicit task ref push, draft PR creation/reuse.
- `skills/fix-code`: reviewed snapshot of the engineering instructions and Git helper, bundled so a new checkout can run tests without your personal skill directory.

The bridge's trusted local configuration supplies workspace/user/channel/model allowlists and optional GitHub owner restrictions. In default channel mode, the bridge reads authoritative public/private channel metadata, then matches its exact name case-insensitively against every accessible repository returned by paginated `gh` results. It requires push permission and rejects missing, ambiguous, archived, read-only, or changed repository identities before coding. `allowedOwners` restricts candidate owners; `channelOwners` provides an explicit owner hint for a channel. Neither a default owner nor punctuation-based name guesses are used. Repository records are bound by numeric GitHub ID, full name, and default branch. If optional `repositoryRouting.localRoot` is configured, an existing exact-name direct child is reused only when it is an ordinary checkout and every origin fetch and push URL matches the selected GitHub repository; an invalid existing child fails closed. A missing child falls back to managed storage. The local or managed storage choice is recorded and stays pinned for the task. Managed clones are keyed by numeric ID below `repositoryRouting.cloneRoot`.

Slack requests supply the task, not an executable, working-directory path, shell flags, recipient, owner, or arbitrary repository. `repo=<alias>` is accepted only in explicit aliases mode. Output cannot choose its reply thread or forge target. Posting tokens are not passed into the coding subprocess environment. Unknown or empty remotes never trigger automatic repository creation.

Retries and follow-ups use the identity recorded during the first repository lookup, even if the Slack channel is later renamed. A GitHub repository rename, transfer, or default-branch change blocks an already bound task. A new top-level task resolves the channel's current name. Missing or changed identities block before implementation rather than silently rerouting work.

Older configuration files with a nonempty `repositories` map and no `repositoryRouting` continue in aliases mode. A config without that map defaults to channel mode. Migration is explicit and should begin with the service stopped and state preserved. Existing alias-bound jobs are not automatically reinterpreted as channel-bound tasks; keep the old config/state available and complete or explicitly retire those jobs as part of migration.

This is a tool for trusted users of a local coding account, not a multi-tenant code execution sandbox. Codex workspace-write limits some filesystem writes; it grants access to the linked Git common directory to permit ordinary commits. Git prohibitions are instructions plus checkpoint detection, not an OS-enforced denial of every Git command. Claude's tool/permission settings do not supply equivalent filesystem/network isolation here. Processes under the same OS account may read accessible credential files even when environment forwarding is restricted. Use dedicated accounts/containers for stronger boundaries.

Phases use fresh model sessions with bounded saved context; they do not silently resume a random CLI session with `--last`. Follow-ups refer to the same persistent task branch but may need an explicit summary for very long work. Attachment download, arbitrary thread-history collection, model pricing discovery, automatic repo creation, CI polling, and native desktop/mobile chat attachment are outside this version.

The default phase models are efficient-strong architecture/review and inexpensive implementation. A fixed phase split cannot guarantee a 20/80 token allocation. Session usage is recorded when the CLI exposes it. A model failure blocks the job instead of triggering a hidden higher-price fallback.

The bridge source checkout and its implementation worktree share a Git backing repository/common directory. Their filesystem locations can vary; do not rely on a fixed checkout path or assume a task worktree is the original source checkout. Keep the backing repository while its worktrees are in use. A non-main baseline may be used for the initial PR after a remote is configured, without creating or changing `main`.
