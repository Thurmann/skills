# Architecture and operating boundaries

- `cli.js`: local configuration, transactional SQLite single-process lease, Socket Mode connection, explicit envelope acknowledgment, worker/outbox timers, diagnostics.
- `protocol.js`: anchored bot command grammar and options parsed only before the separator (`|`, or `--`/`—`/`–`); a plain mention without a command keyword is request data (new task at top level, followup in a task thread); output escaping.
- `store.js`: SQLite WAL, event deduplication, task/job state and durable outbox. State files are private; no secret token values belong in the database.
- `repository-router.js`: authoritative Slack channel metadata lookup, exact case-insensitive repository-name matching over paginated `gh` results (`/user/repos` in user mode, `/installation/repositories` in app mode), owner/hint filtering, write checks (push permission in user mode, installation membership in app mode), optional validated local checkout reuse, and GitHub-ID-keyed managed clones. In app mode each job's prepare step also rechecks that the bound repository is still in the installation.
- `bridge.js`: authorization, immutable thread/repository binding, owner/operator controls, serial queue, bounded phase orchestration, cancellation and recovery.
- `providers/`: one adapter per runtime (claude, codex, gemini, opencode) plus a registry. Each owns its CLI arguments, environment allowlist, JSONL event parser, read-only enforcement and doctor checks; `config.js` picks the default through `runtimePriority`.
- `runner.js`: supported CLI invocation through argument arrays and stdin; explicit models; safe environment forwarding; bounded JSONL and final output; process-group timeout/cancellation.
- `git.js`: GitHub token injection (`githubTokenFile` read and validated on every `gh`/`git` spawn; in app mode a file older than 60 minutes fails the spawn; `GH_TOKEN`/`GITHUB_TOKEN` from the environment are ignored when a file is set, and only `gh`/`git` receive a token), worktree preparation and crash reconciliation, guard checkpoints, remote verification, explicit task ref push, PR creation/reuse (ready for review when the implementer reports `VERIFICATION: complete` and any required review passed, otherwise draft; reused PRs are moved between draft and ready to match), best-effort `AI`/`fix-code`/`slack-bridge` PR labels (`slack-bridge` marks PRs created through the bridge) (missing labels are created without `--force`; failure leaves the PR unlabeled and says so in its body).
- `../../skills/fix-code` (repository root): the single source of the engineering instructions and Git helper; the bridge reads it directly instead of keeping its own copy, and `skillPath` can point elsewhere.

The bridge's trusted local configuration supplies workspace/user/channel/model allowlists and optional GitHub owner restrictions. In default channel mode, the bridge reads authoritative public/private channel metadata, then matches its exact name case-insensitively against every accessible repository returned by paginated `gh` results. It requires push permission in user mode, or installation membership with Contents write in app mode, and rejects missing, ambiguous, archived, read-only, or changed repository identities before coding. `allowedOwners` restricts candidate owners; `channelOwners` provides an explicit owner hint for a channel. Neither a default owner nor punctuation-based name guesses are used. Repository records are bound by numeric GitHub ID, full name, and default branch. If optional `repositoryRouting.localRoot` is configured, an existing exact-name direct child is reused only when it is an ordinary checkout and every origin fetch and push URL matches the selected GitHub repository; an invalid existing child fails closed. A missing child falls back to managed storage. The local or managed storage choice is recorded and stays pinned for the task. Managed clones are keyed by numeric ID below `repositoryRouting.cloneRoot`.

Slack requests supply the task, not an executable, working-directory path, shell flags, recipient, owner, or arbitrary repository. `repo=<alias>` is accepted only in explicit aliases mode. Output cannot choose its reply thread or forge target. Posting tokens are not passed into the coding subprocess environment. Unknown or empty remotes never trigger automatic repository creation.

Retries and follow-ups use the identity recorded during the first repository lookup, even if the Slack channel is later renamed. A GitHub repository rename, transfer, or default-branch change blocks an already bound task. A new top-level task resolves the channel's current name. Missing or changed identities block before implementation rather than silently rerouting work.

Older configuration files with a nonempty `repositories` map and no `repositoryRouting` continue in aliases mode. A config without that map defaults to channel mode. Migration is explicit and should begin with the service stopped and state preserved. Existing alias-bound jobs are not automatically reinterpreted as channel-bound tasks; keep the old config/state available and complete or explicitly retire those jobs as part of migration.

This is a tool for trusted users of a local coding account, not a multi-tenant code execution sandbox. Codex workspace-write limits some filesystem writes; it grants access to the linked Git common directory to permit ordinary commits. Git prohibitions are instructions plus checkpoint detection, not an OS-enforced denial of every Git command. Claude's tool/permission settings do not supply equivalent filesystem/network isolation here. Processes under the same OS account may read accessible credential files even when environment forwarding is restricted. Use dedicated accounts/containers for stronger boundaries.

Each task first runs a read-only `precheck` phase unless the command sets `mode=`. The precheck also returns `estimated_minutes`, which the thread acknowledgement (posted once the mode is known, after the intake-time queued reply, and repeating none of its fields) reports; while the job runs, a timer posts a status update every `statusIntervalMs` (default 5 minutes) and stops when the final result is queued. It classifies the task as simple, medium, or advanced; `fast` is only ever requested explicitly with `mode=fast`. [`skills/fix-code/references/modes.md`](../../../skills/fix-code/references/modes.md) is the single source of truth for the mode, escalation and review rules; the bridge implements them (change `modes.md` first and keep `bridge.js` in line). Bridge-specific behavior: the bridge escalates a simple task to medium by counting the current job's changed logic files (logic files exclude tests, docs and lockfiles) and honoring `SCOPE_EXCEEDED:`; medium jobs run independent review only when the change is not covered by the precheck's logic-file prediction; unreadable precheck output falls back to medium, which then always reviews because no prediction exists; risk flags are limited to security, auth, data/migration and concurrency (other context goes to `notes`), and low confidence plus a risk flag bumps one mode. Each job records a calibration record (`calibration.json` and `job.calibration`) comparing the model's raw mode, adjusted and final modes, and predicted vs. actual logic files. Prompts name only the skill files each phase needs: only the "Precheck" section of `modes.md` for precheck, and never `model-policy.md` or `integrations.md`. Advanced jobs run architect → implementer → mandatory independent review with bounded repair rounds. An explicit `mode=simple` can still escalate to medium (more than 6 logic files or `SCOPE_EXCEEDED:`). An explicit `mode=fast` tells the implementer to compile only (no tests; CI verifies the PR), counts the job's changed logic lines from `git diff --numstat` (each file's larger side), never escalates, and runs independent review only at 8 or more logic lines or 6 or more logic files. An explicit `mode=medium` always runs independent review because there is no file prediction. Escalation and prediction checks count only the current job's commits (from its recorded start commit), not earlier jobs on the task branch. Simple and in-prediction medium jobs publish without independent review, which the final message and PR body state. The implementer ends with one `VERIFICATION: complete` or `VERIFICATION: incomplete: <reason>` line; the bridge publishes a PR ready for review only when it says complete (a missing line counts as incomplete) and otherwise a draft with the reason; followups on an existing PR post the outcome as a PR comment. `retry` keeps the previous job's explicit `mode=`.

Read-only phases (precheck, architect, reviewer) are enforced twice: by each provider's own mode or policy, and by the bridge, which compares `HEAD`, `git status --porcelain` and a content digest of untracked non-ignored files (ignored files are out of scope) before and after the phase and fails the job if either changed. Gemini's headless implementer needs folder trust (`--skip-trust`), and opencode's permissions are injected per run via `OPENCODE_CONFIG_CONTENT`; neither provider is launched with an approval bypass.

Phases use fresh model sessions with bounded saved context; they do not silently resume a random CLI session with `--last`. Follow-ups refer to the same persistent task branch but may need an explicit summary for very long work. Attachment download, arbitrary thread-history collection, model pricing discovery, automatic repo creation, CI polling, and native desktop/mobile chat attachment are outside this version.

The default phase models are efficient-strong architecture/review and inexpensive precheck/implementation. A fixed phase split cannot guarantee a 20/80 token allocation. Session usage is recorded when the CLI exposes it. A model failure blocks the job instead of triggering a hidden higher-price fallback.

The bridge source checkout and its implementation worktree share a Git backing repository/common directory. Their filesystem locations can vary; do not rely on a fixed checkout path or assume a task worktree is the original source checkout. Keep the backing repository while its worktrees are in use. The bridge always prepares a separate worktree in every mode (it runs unattended and may reuse local checkouts), so the skill's in-place option is not used by the bridge. For a genuinely new empty repository, initialize an empty `main` default baseline and target the first PR at `main`; keep all implementation on a separate task branch. Existing repositories keep their current default branch and history.
